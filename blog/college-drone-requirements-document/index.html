Write a requirements document for a student quadcopter project

By YANAPublished 27 October 20263 min read

In this guide

  1. Separate needs from solutions
  2. Make each statement checkable
  3. Build a verification matrix
  4. Example: improve a vague requirement
  5. Review changes deliberately

  7. Questions
  8. References

Write requirements as statements that can be checked and keep them separate from preferred components. Link every requirement to a reason and a verification method. Mark assumptions openly, especially where equipment, performance or permissions remain unknown. Review requirements before changing the design so the team knows what problem it is solving.

Separate needs from solutions

An educational need might be that a learner can inspect and explain the main subsystems. A preferred frame is a design choice that may support that need. Mixing the two makes comparisons difficult. Write the purpose first, then list candidate solutions separately. If a course mandates a particular component, record that as an external constraint rather than pretending it emerged from your evaluation.

Make each statement checkable

Avoid words such as excellent, robust or easy unless you define the observation that would justify them. For documentation, a check might be whether a reviewer can identify the connector and source reference. For a physical dimension, specify the measurement method. Do not invent flight-time, payload or range targets merely to make the document look complete; discuss feasible targets with the supervisor.

Build a verification matrix

Give each requirement an identifier, rationale, planned evidence and status. Possible statuses include proposed, approved, checked and unresolved. Add a reference to the evidence location when a check is completed. A matrix is most useful when it exposes missing work, not when every row is marked complete shortly before submission. Keep failed or inconclusive checks visible.

Example: improve a vague requirement

Replace the drone should be easy to maintain with a narrower documentation requirement: the maintenance sheet must identify each agreed replaceable component and the document used to verify compatibility. A reviewer can inspect that sheet and report omissions. The requirement does not prove repair quality or aircraft reliability, but it provides a clear evidence target within a student project.

Review changes deliberately

When the team selects a different component, ask which requirements and interfaces are affected. Update the rationale instead of rewriting history to suggest the choice was always planned. The CDIO syllabus offers engineering-education context for system-building skills; your project’s requirements remain decisions to agree with its supervisor. Maintain a dated revision record so later reviewers can understand why the scope changed.

  • Keep needs, constraints and component choices separate.
  • Assign each requirement a checkable outcome.
  • Link checks to evidence and unresolved questions.
  • Record approval and revision dates.

Create a five-row requirements matrix

  1. Choose five statements from your project proposal.
  2. Add a rationale and verification method to each.
  3. Rewrite any statement that cannot be checked without guessing.

Questions

Should a component list count as requirements?

It can record imposed constraints or proposed design choices. It usually does not explain the educational need or how success will be verified.

What if a requirement cannot be verified?

Mark it unresolved and discuss a revised scope or evidence method. Do not convert an assumption into a completed result.
