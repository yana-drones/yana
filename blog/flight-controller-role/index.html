What a flight controller does between sensing and motor commands

By YANAPublished 27 October 20263 min read

  7. Questions

A flight controller processes measurements, estimates relevant motion, compares that state with requested behaviour and produces actuator commands. These jobs repeat in a feedback system. Understanding the flow is more useful than treating the board as a mysterious stabiliser, and it helps separate sensing problems from control and output-mapping problems.

A board contains several software jobs

The physical controller is one piece of hardware, but its software performs distinct functions. Draw sensing, state estimation, control and output allocation as separate boxes. A single failure symptom can arise in different boxes. A bad attitude estimate and a correct estimate followed by an incorrect output mapping are different problems even if an observer describes both as poor control.

A requested state needs a matching estimate

A desired angle should be compared with an estimated angle in the same frame and units. A rate controller compares rates instead. PX4’s controller diagrams show several layers of this process, illustrating that position, velocity, attitude and angular rate have distinct roles. An introductory diagram can simplify those layers while keeping their physical meanings separate.

Feedback needs both direction and timing

Suppose a paper model is tilted five degrees away from the requested orientation. The controller needs a response that reduces the relevant error, but a delayed or wrongly signed response can make the situation worse. Use numbered message cards to represent time. This demonstrates why a mathematically sensible rule is not enough without correct interpretation and timely information.

Allocation connects a requested moment to geometry

The controller may request a rotational moment and collective force rather than directly deciding a universal motor order. Allocation converts those requests into outputs based on the actual actuator arrangement. A four-motor square with an unmarked front is incomplete information. This is why geometry, output mapping and rotation conventions belong in the system’s documented configuration.

Do not infer capabilities from a family name

Two boards can differ in sensors, processor resources, interfaces and supported firmware builds. A proposed Pixhawk 2.4.8 should be evaluated as the actual board supplied, not as a guarantee that every current flight-stack feature is available. A learning diagram explains functions; it does not establish software support, safe configuration or operational readiness.

  • Separate sensing, estimation, control and allocation.
  • Compare quantities in matching units and frames.
  • Show timing in the feedback loop.
  • Verify hardware and firmware together.

Run a feedback loop with cards

  1. Assign students the roles of desired angle, sensor, estimator, controller and allocator.
  2. Use a paper model at an illustrative five-degree tilt and pass labelled state cards around the loop.
  3. Introduce one delayed card and one incorrectly signed card separately; discuss the different consequences.
  4. Draw the loop and identify which facts require the actual vehicle geometry or software documentation.

Questions

Does the controller directly know the true aircraft orientation?

It uses measurements and estimation. A displayed orientation is an inferred state with limitations, not direct access to perfect physical truth.

Are controller settings transferable between all four-motor aircraft?

No. Geometry, hardware, firmware and installation affect configuration. Use documentation for the actual assembly and review changes appropriately.
