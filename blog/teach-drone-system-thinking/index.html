Use a quadcopter to teach systems thinking

By YANAPublished 27 October 20263 min read

In this guide

  2. Trace more than one path
  3. Investigate change propagation
  4. Example: changing the lesson equipment
  5. Assess explanations of relationships
  6. Practical activity
  7. Questions
  8. References

Ask learners to trace how a change affects connected parts of the system, then identify which effects need evidence. Use a simple diagram to distinguish power, commands and feedback. Systems thinking becomes useful when learners explain dependencies and uncertainty instead of assuming one component determines the whole aircraft’s behaviour.

Define the system boundary

Choose what the lesson includes: the aircraft, ground station, operator or learning documentation. A diagram that silently changes its boundary can confuse discussion. For an introductory activity, include only the blocks needed to answer the question. Add external dependencies as clearly labelled boxes rather than making the drawing so dense that learners cannot follow a single relationship.

Trace more than one path

A physical cable may relate to power, data or a specific interface, so distinguish the conceptual paths before discussing exact wiring. Use labels as well as colour. Ask learners where information enters the diagram and what would be needed to check a claim. A system-level explanation should not be mistaken for a verified connector-level reference.

Investigate change propagation

Propose a paper change and ask which documents, interfaces and checks would be affected. Do not immediately modify shared hardware. A replacement controller could change mounting, connector arrangements, software compatibility and support needs. The exercise shows why a feature name alone is insufficient for design decisions. Keep proposed consequences separate from consequences established on the actual equipment.

Example: changing the lesson equipment

Imagine replacing a labelled demonstration assembly with a similar-looking unit from another source. Learners list what remains conceptually similar and what must be checked again: identifiers, documentation, interfaces and software context. The class then marks its old diagrams as reference-only until reviewed. This reveals a systems dependency without requiring any powered test or performance claim.

Assess explanations of relationships

Ask for a short explanation that names the starting change, affected elements and missing evidence. Reward a justified uncertainty rather than a confident guess. The CDIO syllabus provides engineering-education context for system-building skills; the paper-change activity here is an original classroom suggestion. Finish by asking which assumption would most affect the conclusion if it proved false.

Ask learners to identify one dependency outside the drawn boundary and explain why it was excluded. This encourages deliberate simplification rather than an assumption that a neat classroom diagram contains every factor affecting a physical aircraft.

  • State the diagram boundary.
  • Distinguish power, command and feedback paths.
  • Trace effects of one proposed change.
  • Name evidence needed before accepting a conclusion.

Run a paper change review

  1. Choose one component replacement without changing hardware.
  2. Mark affected interfaces and documents on a diagram.
  3. Write the first three questions a competent reviewer should resolve.

Questions

Is a systems diagram a wiring diagram?

No. It explains relationships at a chosen level. Verified connector details require separate equipment-specific documentation.

Must this lesson involve operating a drone?

No. Diagrams and an unpowered reference assembly can support the dependency and evidence questions effectively.
