Write a clear report for an educational drone project

By YANAPublished 27 October 20263 min read

In this guide

  1. Explain the problem and scope
  2. Describe the actual configuration
  3. Make the method inspectable
  4. Example: report a partial result
  5. Close with limitations and next work
  6. Practical activity
  7. Questions
  8. References

Lead with the engineering question and the result your evidence actually supports. Describe the configuration, method and limitations before making broader claims. Include enough detail for another student to follow the reasoning, and distinguish proposed improvements from verified outcomes. An honest unresolved result is more useful than an unsupported success statement.

Explain the problem and scope

State who the project helps and which specific question it investigates. Briefly describe the available equipment and constraints. Avoid a long generic history of drones if it does not help assess your work. A focused introduction should tell the reader why the task matters and what the report will establish, with proposed future capabilities kept outside the completed scope.

Describe the actual configuration

Identify components, software versions and relevant changes during the project. Include a labelled diagram or evidence index. A frame model and controller name alone may not explain the system used. If a part identifier is uncertain, say so. For simulated work, describe the simulation context and avoid presenting a software model as a measurement of the physical prototype.

Make the method inspectable

Describe how observations were collected, which comparisons were made and how data was transformed. Link original files where authorised and appropriate. Explain criteria before showing results so the reader can judge whether they were chosen fairly. ArduPilot’s log documentation is useful background for recorded-data projects; source references should match the fields and tools actually used.

Example: report a partial result

A documentation study may find that most endpoints can be verified while one connector remains unresolved. Report the verified subset, the missing source information and the action needed. Do not call the entire system validated. The partial result still improves the project because another learner can see exactly what is known and avoid repeating the same uncertain assumption.

Close with limitations and next work

Separate limitations of the equipment, method and available time. Recommend the next investigation that would reduce uncertainty rather than listing every fashionable feature. Credit contributors accurately and identify reused resources. Use descriptive headings, readable figures and tables with units. A good final report should support handover as well as assessment, so include where the maintained documents and unresolved issues will live.

  • State the question and actual supported result.
  • Document configuration and method.
  • Label simulation and unresolved evidence.
  • Link reproducible files and a practical next step.

Audit a report conclusion

  1. Underline every claim of performance or success.
  2. Link each claim to an observation in the report.
  3. Qualify or remove claims that exceed the available evidence.

Questions

Should unresolved problems be included?

Yes. Explain their effect on conclusions and the evidence needed to resolve them. Hiding them makes the report harder to trust or reuse.

Can proposed upgrades appear in the report?

Yes, in a clearly separated future-work section. Do not describe them as completed capabilities of the prototype.
