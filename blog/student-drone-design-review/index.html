Run a useful design review for a student drone project

By YANAPublished 27 October 20263 min read

In this guide

  1. Send a concise pre-read
  2. Separate facts, assumptions and proposals
  3. Invite specific criticism
  4. Example: review a mounting comparison
  5. Close with decisions and actions
  6. Practical activity
  7. Questions
  8. References

Show the project question, current configuration, evidence and unresolved assumptions before discussing new features. Ask reviewers to identify gaps and decision options rather than deliver a simple pass or fail. Record actions with owners and review dates. A design review supports project reasoning; it is not operational approval unless explicitly defined as such.

Send a concise pre-read

Give reviewers a short scope, system diagram, requirements summary and evidence index. Identify the decisions you want help making. A large slide deck without a clear question can consume the meeting on background explanation. Include known limitations early so reviewers do not have to discover that a claimed result came from a different configuration or simulated dataset.

Separate facts, assumptions and proposals

Use plain labels for evidence already observed, assumptions still under investigation and future changes. For each proposal, explain the expected benefit and the resources needed to evaluate it. Reviewers can then challenge the reasoning without confusing an aspiration with a result. Keep the actual component identifiers and software context available if an interface question arises.

Invite specific criticism

Ask which requirement lacks evidence, which comparison is unfair or which dependency could block the project. Encourage reviewers to state the basis for their concerns. A suggestion should be recorded as a suggestion until the team and supervisor decide whether it belongs in scope. Do not treat every interesting idea as an additional mandatory feature.

Example: review a mounting comparison

A team shows two documented controller-layout proposals and its inspectability criteria. A reviewer notices that one drawing omits cable access. The team records an action to revise that drawing and repeat the comparison, rather than declaring a winning layout during the meeting. The review improves evidence quality without pretending to establish flight behaviour or safety of the proposed modification.

Close with decisions and actions

Read back agreed decisions, deferred questions and action owners. State whether any practical activity remains restricted pending competent review. NASA’s engineering-design resource is relevant background for iteration, while Cornell’s peer-assessment guidance supports constructive feedback. The meeting should leave a smaller, clearer action list, not an expanded project whose new obligations exceed available time.

  • Send the question and evidence index beforehand.
  • Label facts, assumptions and proposals.
  • Request specific evidence-based criticism.
  • Record decisions, owners and review boundaries.

Prepare a three-question review

  1. Choose one requirement, one technical uncertainty and one scope decision.
  2. Attach the evidence needed to discuss each.
  3. Write the resulting action list before ending the meeting.

Questions

Should a review happen only at the end?

No. An earlier review can expose a missing assumption while there is still time to change the method or scope.

Does reviewer approval authorise operation?

Only if that authority and assessment scope were explicitly established. A normal academic review should not be treated as permission to operate an aircraft.
