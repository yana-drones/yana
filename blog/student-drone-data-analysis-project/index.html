Plan a drone data-analysis project with honest evidence

By YANAPublished 27 October 20263 min read

  2. Define a small question
  3. Document units and transformations

Begin with a dataset you can legitimately access and a question its fields can answer. Record its source, software context, units and known limitations before plotting. Preserve original files and label simulation separately. A clear analysis of a limited dataset is stronger than a dramatic chart with unsupported conclusions.

Check data availability first

Do not write a proposal around fields that may never be recorded. Obtain a suitable sample and inspect its structure before choosing the final question. Ask whether sharing is authorised and whether the file includes location or personal details. If real aircraft data is unavailable, a simulation study can still be useful when its scope and origin are explicit.

Define a small question

Examples include whether timestamps are continuous, which fields are missing or how a selected signal changes over a documented interval. Avoid jumping straight to predicting failures or certifying performance. Those claims require much broader validation. A first student project can focus on preparing a reliable, well-explained dataset and identifying what it cannot establish.

Document units and transformations

Keep a data dictionary describing each field used and the source for its meaning. Record filtering, resampling and removed rows. Save raw data separately from derived files. ArduPilot publishes onboard log-message definitions; consult the documentation matching the dataset instead of inferring units from a plausible-looking graph. If a field’s meaning remains uncertain, exclude it from conclusions.

Example: investigate missing records

A team studies a labelled sample log and counts intervals where its selected message is absent. It reports the counting method and shows the raw timestamps for a short example. The team does not automatically call every gap a sensor fault, because recording configuration or data handling may explain it. Its result is a reproducible data-quality observation with alternative explanations.

Make the analysis reproducible

Provide the script, software environment, sample-input instructions and expected outputs. Add a limitations section describing where the method has and has not been tested. Keep charts readable with units, captions and meaningful axes. Another student should be able to recreate the result without finding an undocumented local file or relying on the original author to explain each step.

  • Confirm legitimate data access and provenance.
  • Check fields and units before analysis.
  • Keep raw files and transformations separate.
  • State alternative explanations and limitations.

Write a dataset factsheet

  1. Record source, date context, software and available fields.
  2. Choose one question supported by those fields.
  3. Name two conclusions the dataset cannot justify.

Questions

Can simulator data be used?

Yes, for an explicitly labelled simulation study. Do not present the result as verified real-aircraft performance.

Does a gap prove a sensor failed?

No. Logging settings, transmission, parsing and other factors may explain missing records. Investigate alternatives before assigning a cause.
