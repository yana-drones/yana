Read a drone log plot before diagnosing the aircraft

By YANAPublished 27 October 20263 min read

In this guide

  1. Know where the recording came from
  2. Build a field dictionary first
  3. Choose the time window deliberately
  4. Describe the pattern before naming a cause
  5. Preserve raw data and uncertainty
  6. Practical activity
  7. Questions
  8. References

Begin log analysis by identifying the recording source, field meanings, units, reference frames and time interval. Only then compare behaviour or propose causes. A plausible curve can be misleading if a field is stale, scaled incorrectly or interpreted as the wrong quantity. Observation should precede diagnosis.

Know where the recording came from

An onboard log and a ground-station telemetry log observe the system at different boundaries. ArduPilot’s log overview distinguishes these recording locations. Keep the log type and source with the dataset. A missing field in a ground recording does not automatically mean the onboard controller lacked that information; it may reflect the communication or recording arrangement.

Build a field dictionary first

For every chosen field, write its full name, physical meaning, unit and frame. Mark whether it is a measurement, estimate, command or status. Avoid overlaying similarly named fields until their definitions match. A few carefully interpreted signals are more useful than a large dashboard whose lines are identified only by colour.

Choose the time window deliberately

A whole-session plot can hide a short event, while a tightly cropped graph can remove the context needed to interpret it. Start broad, identify the event and retain a contextual window. Write the selected start and end times in the report. Different sample rates or clock origins can create apparent delays that must be resolved before comparing cause and effect.

Describe the pattern before naming a cause

Say that a value rose after a specified timestamp, reached a certain illustrative level and returned gradually. Then list possible explanations. A control request, physical disturbance and logging artefact can sometimes create superficially similar curves. A diagnosis needs additional evidence capable of distinguishing those possibilities, not just a confident narrative attached to one line.

Preserve raw data and uncertainty

Keep the original file and record any transformations, filtering or omitted samples. If a graph uses fictional classroom data, mark it prominently. Real recordings can contain location or identifiers, so use institution-approved sharing arrangements. The final conclusion should say what the plot establishes and which causal questions remain open rather than declare the entire aircraft healthy or faulty.

  • Identify the recording boundary and log type.
  • Define every field and unit.
  • Align time before comparing curves.
  • Separate observed pattern from suspected cause.

Annotate a deliberately misleading graph

  1. Create a fictional plot with one angle in degrees and a second in radians but give both a vague angle label.
  2. Ask students to identify the missing definitions before interpreting tracking error.
  3. Add separate time origins and require a documented alignment before comparison.
  4. Rewrite the chart title, axes and caption so another reader can understand what is shown and what cannot be concluded.

Questions

Does a gap in a telemetry log prove an onboard failure?

No. The recording boundary matters. Link behaviour, logging choices or unavailable messages can also create gaps.

Can one unusual line identify the failed component?

Usually it supports hypotheses rather than a unique cause. Use definitions, context and additional discriminating evidence before diagnosis.
