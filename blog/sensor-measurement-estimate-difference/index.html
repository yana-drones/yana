Measurement, estimate and command: three different drone data types

By YANAPublished 27 October 20263 min read

In this guide

  2. An estimate brings assumptions
  3. A command is a request rather than a result
  4. Compare like quantities at matched times
  5. Turn a dashboard into an evidence table
  6. Practical activity
  7. Questions
  8. References

A measurement is a sensor observation, an estimate combines observations with a model, and a command requests behaviour. Similar-looking numbers can belong to different stages. Labelling these stages helps students interpret dashboards and compare expected behaviour with evidence without assuming that every displayed value is direct physical truth.

Start from the question each number answers

A sensor value asks what the device observed. An estimated attitude asks what orientation the software considers likely. A desired attitude asks what orientation the control system is trying to achieve. These may all be angles on the same graph, yet their meanings differ. Place a prefix such as measured, estimated or desired in your worksheet column headings.

An estimate brings assumptions

An estimator can combine information that arrives at different rates and has different uncertainties. It also uses assumptions about motion and error. PX4’s navigation-filter documentation describes this sensor-and-model relationship. For an introductory exercise, students can combine two fictional position readings while explaining why a reading known to be unreliable should not receive the same confidence as a better-supported observation.

A command is a request rather than a result

A requested output can be limited by configuration or physical constraints. A hypothetical desired angle of ten degrees and estimated angle of six degrees indicate a difference, but they do not by themselves identify the cause. It could involve timing, limits, disturbance or an incorrect interpretation of fields. Ask for surrounding evidence before attributing the gap to a failed component.

Compare like quantities at matched times

A current command and an older estimate can appear to disagree simply because their timestamps differ. The frame and unit must match too. Before subtracting any two columns, write what they represent and when they were valid. This practice is especially useful when a ground-station display refreshes slowly while the onboard system works with more frequent measurements.

Turn a dashboard into an evidence table

For each displayed value record its stage, unit, reference frame and update information. Include an unknown category when the software does not expose sufficient metadata. Students should be rewarded for identifying missing evidence instead of inventing certainty. The completed table becomes a reliable starting point for later work with real recorded logs.

  • Label measurement, estimate and command explicitly.
  • Match units and frames before comparison.
  • Use timestamps rather than screen position.
  • Record confidence and unavailable metadata.

Interpret a fictional three-column log

  1. Create a paper log with time, desired angle and estimated angle; add one deliberately delayed estimate.
  2. Ask teams to identify which columns are requests and which describe inferred state.
  3. Let them realign the delayed column and explain how the apparent error changes.
  4. Add two fictional sensor readings with different uncertainties and ask what evidence would justify trusting one more strongly.

Questions

Is an estimated position a raw GNSS reading?

Not necessarily. The flight stack may combine GNSS with inertial and other information. Check the exact field definition rather than relying on its dashboard label.

Does a small tracking error prove the system is safe?

No. One error metric cannot establish the health of every sensor, structure or operating condition. It answers only a defined comparison within the available evidence.
