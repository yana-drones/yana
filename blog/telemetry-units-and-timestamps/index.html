Telemetry units and timestamps: fix interpretation before plotting

By YANAPublished 27 October 20263 min read

Telemetry fields can use different units, scales, time origins and unknown-value conventions. A timestamp may count since boot rather than represent wall-clock time. Resolve each field from its exact message definition before plotting, converting or combining data. A valid zero must remain distinguishable from an unavailable measurement.

A number needs a schema

A stored integer of 1,000 might represent milliseconds, millimetres or another scaled quantity. Its meaning comes from the message and field definition, not its magnitude alone. MAVLink’s common message reference documents field types, units and special values. Use the exact message name in your worksheet so the dictionary remains tied to a primary definition.

Convert scale explicitly

For a fictional classroom field defined as centimetres, a stored value of 250 represents 2.5 metres. Keep a raw-value column and a converted-value column rather than overwriting the original. Write the conversion factor with units. If students cannot explain where that factor came from, the processed plot is not yet a reliable representation of the data.

Identify clock origin and unit separately

Milliseconds since boot and seconds on a wall clock answer different timing questions. Two devices can start their counters at different moments. A graph labelled time does not reveal whether they share an origin. A classroom example can align two invented timelines using a documented common event, then explain the uncertainty introduced by that alignment.

Unknown is not the same as zero

Some fields use sentinel values or flags to indicate unavailable data. The correct interpretation is message-specific. Replacing every unknown with zero can invent a dramatic drop that never occurred physically. Mark unavailable samples visibly or omit them through a documented rule, while retaining the original values for review. Do not guess the convention from another message.

Validate one known case by hand

Before plotting a complete recording, manually convert a few samples with obvious physical meaning and check their order in time. Include a negative value, an unavailable value and a valid zero where the schema allows them. Small examples reveal mistakes that can remain hidden inside a smooth graph. Keep component identity alongside time when several sources are present.

  • Use the exact message and field definition.
  • Retain raw values beside converted values.
  • Record timestamp unit and origin.
  • Handle unavailable values without inventing zeros.

Repair a fictional telemetry table

  1. Provide centimetre position values and millisecond boot times, plus one explicitly documented unavailable sentinel.
  2. Ask students to create converted metre and second columns without changing the originals.
  3. Add a second device whose boot clock starts later and align it using a stated common event.
  4. Plot the result with a visible gap for the unavailable sample and explain why zero would have created a false event.

Questions

Can I assume every timestamp is UTC?

No. It may use a boot-relative or other documented origin and a particular unit. Read the exact message definition.

Is a zero field always valid data?

No universal rule applies. Some fields use zero or another special value for unavailable information; others use zero as a valid measurement.
