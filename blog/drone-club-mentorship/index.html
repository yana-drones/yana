Build a mentorship process for a drone-learning club

By YANAPublished 27 October 20263 min read

In this guide

  1. Define the mentor’s role
  2. Model evidence-seeking behaviour
  3. Use tasks that leave learner ownership
  4. Example: a diagram coaching session
  5. Review mentors as well as learners
  6. Practical activity
  7. Questions
  8. References

Define what mentors can explain, review and supervise, then give them a clear route for questions beyond that scope. Pair a small learning task with feedback instead of letting mentors simply complete work for beginners. Experience is useful evidence to discuss, but it does not automatically establish authority for every practical activity.

Define the mentor’s role

A peer mentor might help a newcomer read the system diagram, locate documentation or improve a notebook entry. Those responsibilities differ from authorising powered work or judging aircraft readiness. Write the boundaries in plain language. Make the institutional coordinator and competent technical reviewer visible so mentors are not pressured to answer questions beyond their knowledge.

Model evidence-seeking behaviour

Ask mentors to explain how they know something and where the relevant source lives. A response such as let us verify the actual identifier can teach a better habit than an immediate guess. Preserve unresolved questions in a shared list. Avoid using memory of a different build as the only basis for advising someone about the current equipment.

Use tasks that leave learner ownership

A mentor should prompt the learner to make the diagram, explanation or record rather than taking over the task. Ask open questions and allow thinking time. Cornell’s peer-assessment guidance supports constructive feedback as an educational practice; it does not establish technical authority. Agree how feedback will be reviewed when a disagreement involves equipment-specific facts.

Example: a diagram coaching session

A beginner draws a command path that skips a subsystem. The mentor asks what relationship the missing block explains and points to a verified reference, rather than redrawing the whole map. The learner revises it and describes the change. If the question becomes connector-specific, both record it for the responsible reviewer instead of moving directly to hardware experimentation.

Review mentors as well as learners

Ask beginners whether the support was understandable and whether they had space to contribute. Give mentors feedback on clarity, source use and escalation decisions. Rotate mentorship opportunities where appropriate, but do not present a peer role as a professional qualification. If YANA professional-led training is requested, the actual facilitator and credentials still need independent confirmation in the written proposal.

Invite mentors to say what evidence would change their advice. This models intellectual flexibility and helps beginners distinguish a well-supported explanation from a preference based on one previous project, especially when the present equipment differs from earlier examples.

  • Define explanation and supervision boundaries.
  • Require source-based reasoning.
  • Keep the learner responsible for their output.
  • Provide an escalation and mentor-feedback route.

Write a mentor response guide

  1. Choose one common newcomer question.
  2. Write a prompt, a source and an escalation condition.
  3. Practise responding without taking over the learner’s task.

Questions

Can a senior student supervise every activity?

Do not assume that. Supervision authority and competence must be agreed for the specific task through the responsible host arrangements.

Should mentors always give the answer immediately?

Not necessarily. A well-chosen question and reliable source can help the learner build a reusable reasoning process.
