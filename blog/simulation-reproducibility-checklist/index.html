Make a drone simulation experiment reproducible

A reproducible simulation record identifies software versions, model assets, configuration, initial conditions and analysis steps. A screenshot alone is insufficient. Preserve the original output and explain intentional changes, so a second student can repeat the question and understand differences instead of guessing which hidden setting produced the result.

Define the experiment before naming the software

Write the question, the quantity to observe and the expected comparison. For example, ask whether two analysis windows report the same average of one supplied signal. This makes the experiment assessable even if the chosen tool changes. An impressive scene or complex model does not improve a poorly defined question.

Capture the complete version relationship

Flight software, simulator and integration components can evolve separately. ArduPilot’s Gazebo guide distinguishes simulator generations and the integration plugin, showing why “used Gazebo” is not sufficient metadata. Record exact versions or revision identifiers where available. Follow the official guidance for that combination rather than assuming that instructions from different periods can be merged without consequence.

Keep starting conditions and randomness visible

A vehicle model’s initial pose, environment and sensor assumptions influence results. If a scenario includes randomness, record how it was controlled or acknowledge when exact repeatability is not available. A classroom worksheet can use an instructor-provided fixed dataset to isolate analysis choices before introducing varied simulation runs. Do not treat unexplained variation as proof that the software is unreliable.

Preserve raw output and processing steps

Save the original recording separately from filtered, cropped or converted data. Record units, time conversions, excluded intervals and any resampling. Two students can use the same run and still produce different plots because their analysis steps differ. A simple readable recipe with exact inputs is more useful than a screenshot containing no traceable data.

Ask another team to reproduce the interpretation

Give the second team your record without verbal hints. Ask them to recreate the intended plot or calculation and identify ambiguities. Their questions reveal missing metadata. The review should distinguish successful reproduction of an analysis from validation of the underlying model: repeating the same assumption consistently does not prove that assumption matches a real aircraft.

  • Record the question and chosen quantity.
  • Identify stack, simulator, plugin and model versions.
  • Preserve starting conditions and raw output.
  • Document every analysis transformation.

Exchange incomplete experiment records

  1. Create a fictional simulation record with a model name, output table and one missing item such as time unit or starting condition.
  2. Exchange records and ask a second team to reproduce a plot without asking verbal questions.
  3. Have them mark every assumption they had to make.
  4. Revise the record and explain which additions improve repeatability and which questions about model validity remain unresolved.

Questions

Is a video of a simulated flight enough for reproducibility?

No. It can illustrate behaviour but usually omits versions, configuration, model details and raw data needed to repeat or analyse the experiment.

Does reproducing a result prove the model is physically accurate?

No. Reproducibility concerns repeating the method and interpretation. Physical validity requires additional evidence comparing the model with appropriate real-world measurements.
